# The two Grafana dashboard sets, and which one B4 should port

B4 of [containerization_strategy.md](containerization_strategy.md) has to
port a dashboard set to QuestDB SQL, and two sets exist that are not
versions of each other. This file is the comparison that was supposed to
settle which one — how far it can be taken from committed evidence, and
exactly what is left that needs the boat.

Everything below is read off files in this repo or off git history. Nothing
here was read off the boat's running Grafana: the session that wrote it
could not reach the tailnet.

## The two sets

| | Boat's native Grafana | This repo |
| --- | --- | --- |
| Dashboards | 5 | 6 |
| Panels | 76 | 141 |
| Query targets | 100, InfluxQL | 195, Flux |
| Origin | copied from `meri-imperiumi/lille-oe` | generated by `scripts/build_dashboards.py` |
| Buckets read | `symphony` | `signalk`, `telegraf`, `influxdb` |

The boat's five are recoverable from git without boat access. Commit
02afad7 (2026-08-11, "Import the boat's Grafana dashboards and document the
legacy stack") is a verbatim export of them, with one documented
modification: all 162 panel-level datasource references rewritten to uid
`influxdb-symphony`. The export self-checks against the independent survey
in [legacy_openplotter_stack.md](legacy_openplotter_stack.md) — panel
counts per dashboard (Electricity 19, Life support 12, Navigation 12,
Navstation under way 22, Weather 11 = 76) and the 162 datasource
references both match exactly. Commit 1ce4e87 (2026-08-14) then replaced
those files with the generated six, so the boat's five survive only at
02afad7 and earlier.

## What the boat's five actually contain

`signalk_paths.md` records that these were copied from Lille Ø unmodified.
The export bears that out beyond doubt:

- **23 of the 76 panels are library-panel references**, all created in 2022
  in another Grafana by a user named `bergie`, in a folder named `General`.
  Library panel definitions live in the Grafana database, not in dashboard
  JSON.
- **One panel is a text panel embedding an iframe** pointed at
  `http://lille-oe-pi.local/@signalk/freeboard-sk/` — another vessel's
  hostname, hardcoded.
- **Five panels read `networking.lte.*`** (bars, rx, tx, rssi) — an uplink
  this boat does not have.

Classifying all 76 panels against the published/absent path lists in
[signalk_paths.md](signalk_paths.md):

| Panels | Status |
| --- | --- |
| 21 | reference only paths this boat publishes |
| 35 | reference at least one path this boat has **never** published |
| 15 | reference paths whose status is not recorded either way |
| 4 | library-panel references carrying **no inline model at all** |
| 1 | the `lille-oe-pi.local` iframe |

The 4 with no inline model are all on Electricity — "State of Charge",
"Battery time remaining", "Wind speed", "Battery current". Their JSON
carries only `gridPos`, `id`, `libraryPanel`, `title` and `type`. What
they query cannot be recovered from the export at all; it exists only in a
Grafana `library_element` row.

Of the 100 query targets across the five, 98 are InfluxQL query-builder
targets, 1 is raw InfluxQL and 1 is the empty target on the iframe text
panel. **There is no Flux in them.** This
contradicts `legacy_openplotter_stack.md`, which says "Queries are InfluxQL
throughout, apart from a few Flux panels in Life support" — the Life
support panel that is not a builder target ("Battery current") holds raw
InfluxQL, `SELECT mean("value") FROM "electrical.batteries.house.current"
WHERE $timeFilter GROUP BY time($__interval) fill(null)`. Flagged rather
than corrected in that file, because the export is a 2026-08-11 snapshot
and the survey it disagrees with was taken from the live Grafana on
2026-08-14; the boat can settle it and this session could not.

## What each set covers

The two sets share 17 SignalK paths. The boat's five reference 36 the
generated six do not; the generated six reference 93 the boat's five do
not.

**Only in the generated six** — per-cell voltages and protection/FET state
for both JBD packs, house-bank consumed charge and discharge-since-full,
Cerbo digital inputs and relays, Bluetooth sensor reachability and RSSI for
all four BT devices, GNSS quality (satellites, HDOP, fix type, antenna
altitude), a position geomap, the full barometer trend tree (1 h/3 h/12 h
ago and deltas, tendency, severity, predicted front), tide, sunrise/sunset,
moon phase, NOAA space weather, and the entire **System health** dashboard
— 25 panels reading Telegraf (`cpu`, `mem`, `swap`, `disk`, `diskio`,
`net`, `procstat`, `chrony`, `rpi_health`) with no counterpart aboard.

**Only in the boat's five**, split by whether it could work here:

*Cannot work — this boat has never published the path* (35 panels): solar
array yield per panel, MultiPlus AC in/out, alternator and hydrogenerator
output, total panel power, depth, apparent wind speed and angle, fresh
water and diesel tank levels, engine hours, true heading, speed through
water, polar speed, anchor radius, and the LTE uplink group.

*Status not recorded — this is the part that needs the boat* (15 panels):

| Path | Boat panel(s) | Note |
| --- | --- | --- |
| `environment.outside.pressure.prediction.quadrant` | Weather forecast | `signalk_paths.md` says the "full trend/prediction tree" is present but does not name this leaf |
| `environment.outside.pressure.prediction.beaufort` | Wind forecast | same |
| `electrical.batteries.starter.voltage` | Starter battery | only `house`, `0146`, `5C90` are recorded as present |
| `electrical.chargers.multiplus.chargingMode`, `electrical.venus.acSource` | MultiPlus | only `venus.{dcPower,state}` and `chargers.VictronACCharger.*` are recorded |
| `environment.inside.{engineRoom,heads,mainCabin,saloon,wardrobe}.{temperature,relativeHumidity}`, `environment.inside.temperature` | Temperature, Humidity, Inside temperature, Inside | no per-cabin sensor path is recorded anywhere; the BME680 entry in `priorities.md` records that the one inside sensor's temperature channel is unmapped |
| `environment.outside.heatIndexTemperature` | Outside feels like (×3) | the generated set uses `environment.outside.feelsLikeTemperature` for the same idea |
| `environment.outside.humidity` | Relative humidity, Humidity | the generated set uses `environment.outside.relativeHumidity` |
| `environment.wind.speedOverGround` | Wind speed (×2) | the generated set uses `environment.wind.speedTrue` |
| `environment.sun` | System | day/night band on the weather state timeline |

Four of these are naming variants of something the generated set already
covers (`heatIndexTemperature`/`feelsLikeTemperature`,
`humidity`/`relativeHumidity`, `wind.speedOverGround`/`wind.speedTrue`) —
if the boat's variant is the one carrying data, the generated panel is
pointed at the wrong measurement, and vice versa. That is a real question
about the generated set, not only about the legacy one.

## What the imported five show that the generated six don't

Restricting to content that is not another vessel's hardware, the answer is
six ideas, and only the first is backed by a path the repo records as
present:

1. **Barometer forecast in words** — `pressure.prediction.quadrant` and
   `.beaufort`, rendered as `logs` panels. The generated Weather dashboard
   carries the numeric barometer tree and `prediction.front.{prognose,wind}`
   but nothing from these two leaves.
2. Starter-battery voltage.
3. MultiPlus charging mode and AC source as a state timeline.
4. Cabin-by-cabin temperature and humidity.
5. `environment.sun` as a day/night band.
6. **A chartplotter embed** — the iframe panel. Broken as it stands because
   it names Lille Ø's host, but repointed at this boat's own
   `@signalk/freeboard-sk` it is a feature the generated set has no
   equivalent of.

Everything else the boat's five show is either already in the generated six
or is hardware Symphony does not have.

## Neither set runs against the boat's Grafana today

This is the finding that reframes the choice, and it applies to both.

- **The boat's five** point 158 of 162 datasource references at uid
  `eWjoLxAnk`, which does not exist on that Grafana
  (`legacy_openplotter_stack.md`, measured 2026-08-14). Separately, 23 of
  76 panels are library-panel references to another vessel's Grafana.
  Whether the boat's Grafana holds matching `library_element` rows is
  **not recorded anywhere in this repo** — it is one of the things that
  needs eyes on the boat.
- **The generated six** query buckets `signalk`, `telegraf` and `influxdb`.
  The last measured state of the boat's InfluxDB is a single bucket
  `symphony` (`legacy_openplotter_stack.md`, and the 2026-08-11 log entry
  recording the schema read off the running server).
  The four-bucket split arrived in commit 89e9d10, which added a
  bucket-creation procedure to RUNBOOK rather than reporting buckets
  created; **no log entry records it having been applied to the boat.**
  Until it is, every generated query reads a bucket that does not exist.

So "what Mark actually looks at today" needs care as an argument for the
legacy set. What is verified is that those five are what is *installed* on
the boat's Grafana. Whether their panels render — given the dangling
datasource uid and the library-panel references — is not established by
anything committed.

## What this costs each way

**Teaching the generator to emit SQL.** All 195 generated queries come from
exactly two functions: `flux()` and `flux_position()` in
`scripts/build_dashboards.py`, together about 60 lines. Those are the only
two places in the file that emit `from(bucket:`; every panel in the spec
routes through them. The Telegraf panels go through the same `flux()` via a
`_tg()` options helper. `scripts/test_dashboards.py` already checks
regeneration-identity, datasource uids, unit conversions, layout, bucket
routing and seed coverage offline, and passes on the current tree; its
bucket-routing check is the one that would need rewriting for a
schema-per-table store.

**Hand-porting the boat's 76 panels.** 35 of them query paths this boat has
never published, 5 more read a nonexistent LTE uplink, 1 embeds another
vessel's hostname, and 4 cannot be read at all without the boat's Grafana
database. That leaves 21 panels known to be portable and 15 that cannot be
judged from here.

## What still needs the boat

1. Do the boat's five actually render? Specifically, does that Grafana hold
   `library_element` rows for the 23 referenced library panels, and what do
   the 4 model-less Electricity panels query?
2. Which of the 15 unrecorded paths carry data — above all the two barometer
   prediction leaves, and the per-cabin temperature/humidity group.
3. Which side of each of the four naming variants is live
   (`heatIndexTemperature` vs `feelsLikeTemperature`, `humidity` vs
   `relativeHumidity`, `wind.speedOverGround` vs `wind.speedTrue`).
4. Do the four buckets exist on the boat's InfluxDB yet?
5. Has anything changed in the boat's Grafana since the 2026-08-11 export?
6. Whether the Flux-in-Life-support disagreement above is an error in
   `legacy_openplotter_stack.md` or a change made aboard after 08-11.

`scripts/audit_dashboard_paths.py` answers 2, 3 and 4 directly and has to
run on the boat — it reads the InfluxDB token from the live plugin config.
Question 1 needs the Grafana SQLite database, read the way
`legacy_openplotter_stack.md` describes (`sqlite3` is not installed on the
Pi; use Python's module against a `file:...?mode=ro` URI).
